# 聊天上下文压缩 + 提升缓存命中：探索方案

> 状态：第 5 节（用量 + 断点诊断）、3.1（迟滞截断）、3.2（缓存友好世界书开关 + 易变宏提示）、
> 第 4 节第一行（历史去思维链）、3.5 中的 `include_usage` 与 `prompt_cache_key`（仅官方 OpenAI）**已实现**，
> 回归脚本 `npm run verify:prompt-cache`。未做：3.3 前情提要、3.4 演绎前缀统一、真实分词器、llama.cpp 参数。
> 范围：`services/prompt/*`、`services/memory/*`、`services/provider/openaiCompatible.ts`、`stores/generation.ts`

---

## 0. 结论

1. **目前长对话几乎吃不到前缀缓存。** 历史从最旧一条开始逐条截断，对话一旦超过预算，每一轮开头的那条历史都不一样，缓存只能命中系统块。而系统块里还夹着按关键词激活的世界书，所以常常连系统块也命中不了。
2. **命中率现在是看不到的。** 请求里没带 `stream_options.include_usage`，也没读 `prompt_cache_hit_tokens` / `cached_tokens`，优化前后的差别没法量化。
3. 收益最大的三处改动：
   - **按块截断 + 迟滞**：一次丢一大段，之后连续多轮前缀保持不变；
   - **把会变的内容搬到尾部**：关键词激活的世界书、召回片段、状态卡、时间宏都往后放；
   - **补上用量统计**，并做一个断点诊断：告诉用户这次请求从第几条消息开始和上次不一样。
4. 粗略估算：16k 上下文的长对话，输入 token 的**计费成本**能降 60%–80%（按 DeepSeek 命中价约为未命中价的 1/10 计）。token **数量**不变，省的是钱和首字延迟。真正减少 token 数靠第 4 节的压缩手段。

## 1. 各家缓存机制（决定怎么设计）

| 服务 | 机制 | 要点 |
|---|---|---|
| DeepSeek | 自动硬盘缓存，按前缀匹配 | 命中部分按低价计（约为未命中价的 1/10～1/50，因模型和时段而异）；usage 里返回 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens` |
| OpenAI 及兼容接口 | 自动缓存，需 ≥1024 token，按 128 token 递增匹配 | `usage.prompt_tokens_details.cached_tokens`；可传 `prompt_cache_key` 帮助路由到同一台机器 |
| Anthropic（原生协议） | 需要手动加 `cache_control` 断点 | 写入缓存要额外收费，读取约 1/10；走 OpenAI 兼容中转时通常用不了 |
| llama.cpp / Ollama（本地） | 复用 KV cache | 不省钱，但能明显缩短首字延迟，尤其是 6GB 显卡；llama.cpp 用 `cache_prompt: true` |

**共同规律**：从第一个不同的 token 开始，后面全部算未命中。所以要把稳定的内容放前面、会变的内容放后面，保证每轮只有末尾在变。

## 2. 现状：哪些地方破坏了前缀

当前组装顺序（`builder.ts` 头部注释）：

```
主提示词 → WI before → 角色设定 → 性格 → 场景 → WI after → 用户设定 → [演绎成员]
→ 示例 → [开始新对话] → 历史(内含深度注入) → group nudge → PHI
```

开启 `squashSystemMessages` 后，前面这些相邻的 system 块会合并成**一条**消息，其中任何一个字变了，整条都算未命中。

按影响从大到小：

| # | 破坏点 | 位置 | 影响 |
|---|---|---|---|
| A | **历史从头逐条截断** | `budget.ts takeHistory()`：从新往旧取，放不下就停 | 对话超过预算后，每轮都会从最前面挤掉 1～2 条，历史部分**每轮都不命中**。长对话里这是最大的成本来源 |
| B | **关键词激活的世界书在前缀里** | `worldInfoBefore/After` 位于系统块中间 | 这一轮聊到「剑」激活一条、下一轮没提就消失 → 从角色设定开始全部未命中。记忆书（状态卡、向量召回）也并进了 `loreSources`，如果条目用了 before/after 位置，同样会这样 |
| C | **会变的宏** | `macro/registry.ts`：`time/date/weekday`、`idle_duration`、`random/roll`（用 `Math.random`） | 放在主提示词或角色卡里，每轮都会变，缓存从第一条消息就断了。`pick` 基于 `fnv1a` 是稳定的，没问题 |
| D | **演绎换发言人** | `mandatory` 按 `input.speaker` 组装；SWAP 模式换卡；`{{char}}` 每轮不同 | 演绎里每换一个人，系统块整体就变了。几个角色轮流说话时几乎命中不了 |
| E | **示例块被预算挤掉** | 非 `pinExamples` 时历史优先，示例吃剩下的预算 | 示例夹在系统块和历史之间，保留下来的示例块数随历史长度波动，前缀跟着变 |
| F | 深度注入 | `injectAtDepths` 放在距末尾 N 条的位置 | 只影响末尾几条，损失小，属于合理设计。但 `status`/`constraint` 的 depth 设得很大时，影响范围会变大 |
| G | 世界书的概率 / sticky / cooldown | `worldinfo/engine.ts` | 重新生成（swipe）时，概率重新抽签可能导致前缀不同 |

另外两个问题：

- **不统计用量**：`streamChat` 不请求 usage，`parseSSE` 也不读，所以缓存命中率和每条消息的真实 token 数都拿不到。
- **token 是估算的**：`tokens.ts` 按「CJK 字 1 token、其余 4 字符 1 token」估算，误差 10%–30%。为防超长，预算只能留余量，这部分 token 相当于浪费了。

辅助调用（状态卡提炼每 12 条一次、`promptFromLLM` 生图转写）各有独立的提示词，本身不大，但同样可以用固定前缀来提高命中。

## 3. 提升缓存命中的方案

### 3.1 按块截断 + 迟滞（解决 A，收益最大）

改 `takeHistory`：历史放不下时**不再每次只挤掉 1 条**，而是一次砍到预算的某个水位线以下（比如只保留 70%），并记下「截断起点 seq」存在 chat_metadata 里。之后几轮只要总量没超过预算，起点就不动，前缀也就保持不变。

```
预算 12k：历史长到 12k → 从头砍到 8.4k（起点=seq 57）
接下来 ~10 轮：起点仍是 57，前缀完全一致 → 命中
再次超 12k → 起点跳到 seq 83
```

- 代价：平均少带约 15% 的历史，可以用 3.3 的「前情提要」补回来。
- 水位线做成设置项（默认 0.7），设为 1.0 等于现在的行为。
- `fitWithinBudget` 要能读写这个起点，需要通过 `BuildPromptInput` 传入；dryRun（预览）时只读不写。

### 3.2 布局分层：稳定前缀 / 滚动历史 / 易变尾部（解决 B、C、E）

```
┌ 稳定层（除非用户改设置，否则不变）
│  主提示词 · 角色设定/性格/场景 · 用户设定 · 常驻世界书(constant) · 固定示例
├ 半稳定层（少量事件时才变）
│  前情提要（3.3，只在截断起点跳动时更新）
├ 历史（从截断起点开始，只往末尾追加）
└ 易变尾部（每轮都可能变，统一放在 depth 0～2）
   关键词激活的世界书 · 向量召回 · 状态卡 · 角色状态 · 时间类宏 · group nudge · PHI
```

具体改动：
- 新增设置项「缓存友好布局」（默认关闭，以保证和 ST 行为一致）。开启后，**非 constant** 的 before/after 世界书条目改为按深度注入到尾部，constant 条目留在前缀。
- 时间类宏：开启后在前缀里把它们冻结到「按天」（`date` 不受影响，`time` 冻结成当天首次调用时的值），或者提示用户把时间放进约束提示词（depth 0）。
- 增加宏的易变性标记（在 registry 里给宏标 `volatile`）。PromptPreview 检测到前缀里用了易变宏时给出警告：「此处的 {{time}} 会让缓存每轮失效」。
- 示例块：一个会话第一次决定带几块示例后就锁住，不再随预算浮动；或者建议打开 `pinExamples`。

### 3.3 前情提要块（补偿 3.1 截掉的历史）

截断起点跳动时，把被砍掉那一段交给模型做一次摘要，追加到「前情提要」里，放在历史之前。

- 更新频率 = 截断起点跳动的频率，每几十轮一次，每次更新会让缓存失效一次。
- 和现有的**状态卡**不冲突：状态卡是「此刻的事实」，放在尾部 depth 2，每 12 条更新一次；前情提要是「已离开窗口的剧情」，放在前缀之后，很少更新。
- ⚠️ 以前删掉过「滚动摘要」。如果当时是觉得它没用，可以不做这一项，只做 3.1，靠现有的状态卡加向量召回来补。**这一项需要你决定。**

### 3.4 演绎（解决 D）

- 开启缓存友好布局后，把「全体成员设定」统一放进前缀（相当于强制用 APPEND 模式拼接所有卡），「当前发言者是谁」只在尾部用 nudge 说明，比如「现在以 {{char}} 的身份回复」。
- 主提示词里的 `{{char}}` 在演绎中会随发言人变化，诊断工具应把它标为易变。
- 代价：前缀变长，因为每轮都带上所有人的卡。但这部分都能命中，计费反而更便宜。

### 3.5 各服务的专用参数

在 `ModelService` 上加「缓存策略」字段，由服务类型决定往请求里加什么：
- OpenAI 兼容：`prompt_cache_key = chatId`（不支持的中转一般会忽略）；
- llama.cpp：`cache_prompt: true`，可选 `id_slot`；
- Anthropic 原生（以后接入时）：在稳定层末尾和历史截断起点各放一个 `cache_control` 断点；
- 所有流式请求：`stream_options: { include_usage: true }`。

## 4. 减少 token 数的压缩手段

| 手段 | 做法 | 预期 | 风险 |
|---|---|---|---|
| 历史净化 | 发送前去掉 `<think>`、残留的 `<status>`、多余空行和 Markdown 装饰；`stripThink` 已有，可以复用 | 推理模型的回复能省 20%+ | 低 |
| 超长旧回复截尾 | 距末尾超过 N 条、且超过 M 字的 AI 回复，只保留开头 + 结尾 | 中等 | 可能丢细节，默认关闭 |
| 前情提要替代原文 | 见 3.3 | 能压缩掉大量旧历史 | 摘要可能失真 |
| 世界书预算收紧 | 召回和关键词条目共享一个独立的小预算，别和历史抢 | 稳定 | 需要调参 |
| 真实分词器 | 用 transformers.js（项目里已经有）按模型加载分词器，或让服务端 `/tokenize` 精确计数；安全余量从估算误差降到 ~2% | 多带 10%+ 有效历史，或更少截断 | 首次加载会耗时 |
| 状态卡提炼复用主对话前缀 | 提炼请求 = 主对话已缓存的前缀 + 末尾加一条「请更新状态卡」指令 | 输入更长，但大部分命中；换来无需另发 3000 字对话 | 要实测对比成本 |

## 5. 可观测性（应该最先做）

1. `streamChat` 带上 `include_usage`，`parseSSE` 解析最后一个 usage 块，兼容 DeepSeek 和 OpenAI 两种字段名，存进 `MessageExtra.usage`：`{ prompt, completion, cached }`。
2. 消息气泡或 PromptPreview 显示「输入 9.8k（缓存 8.9k，91%）」。
3. **断点诊断**：每次发送时对每条消息算 `fnv1a`（项目里已有）得到签名序列，存入内存中每个会话的上一次签名。PromptPreview 标出「从第 k 条开始与上次不同，原因：世界书条目 X 激活 / 历史起点前移 / 宏 {{time}}」。
4. 这样 3.x 的每一项改完都能直接看到命中率的变化。

## 6. 收益估算（示意，非实测）

假设：上下文 16k、回复 1k，系统块 3k，历史填满约 12k，每轮新增约 600 token。

| 场景 | 每轮能命中的前缀 | 命中占比 |
|---|---|---|
| 现状、世界书稳定 | 只有系统块 3k | ~20% |
| 现状、世界书每轮变化 | 主提示词那一小段 | ~0–5% |
| 3.1 + 3.2 | 除末尾新消息和尾部注入外全部命中 | 截断后的 ~10 轮里约 90%；跳动那一轮 ~20% |

按命中价 = 未命中价的 1/10，**输入成本降到现在的约 25%–35%**。swipe / 重新生成时的前缀几乎完全一致，命中率接近 100%（前提是 3.2 已把概率世界书移到尾部）。

## 7. 建议顺序

1. **可观测性**（第 5 节）：零风险，先把基线量出来。
2. **按块截断 + 迟滞**（3.1）：改动集中在 `budget.ts` 和 `chat_metadata`，收益最大。
3. **历史净化**（第 4 节第一行）。
4. **缓存友好布局开关**（3.2）+ 易变宏警告。
5. 服务专用参数（3.5）。
6. 按需：演绎前缀统一（3.4）、真实分词器、前情提要（3.3，需要你决定）。

回归依据：`verify:status`、`verify:group-mentions` 加上 PromptPreview 的对比。另外建议新增 `verify:prompt-cache`：模拟 30 轮对话，断言相邻两轮的签名公共前缀长度。
